# Release checks

The `Scottland fast checks` workflow tests pull-request merge refs and merge-group refs for `main` and `0.3`. Fresh GitHub-hosted x86_64 and ARM VMs build the Rust tools, run locked Rust tests and the pure C++ plugin units, including work from public-fork PRs. These cloud jobs are partial checks: the compatible Wayfire/wlroots plugin build and owned headless smoke still need a validated image or local dedicated runner. On each registered local architecture, the full job builds the plugin and tools, runs locked Rust unit tests and the inertia, navigation, pairing, peek, rail-make-room, spread and windowing plugin unit suites. Its isolated headless suite checks output IPC, a mapped window, focus and a requested geometry change with bounded state waits. The longer hint-outline and spread acceptance suites remain in separate acceptance rounds. Headless checks are preflight only; they do not establish physical GPU or real-session acceptance.

Register repository-scoped local x86_64 runners with the shared `scottland-ci-x86_64` label only after dedicated account and runtime setup is approved; the available runner can claim the one local full-check job. Local runners need a dedicated noninteractive account with `SCOTTLAND_CI_DEDICATED=1`, an existing owned `XDG_RUNTIME_DIR`, installed build and headless dependencies, and a checkout outside `/tmp`. The account must not own a live graphical session. The fast-check script refuses to start if those conditions fail and preserves scratch on uncertain cleanup. Shared device test machines retain manual adapter and graphics coverage rather than required CI service. Keep branch rules and merge queue disabled until the intended required cloud and local jobs pass on a PR and a merge-group ref. Public fork pull requests cannot execute on local self-hosted runners.

When `main` moves, open or update a PR from `main` to `0.3`. Resolve conflicts on a branch from the current `0.3` tip if a direct PR is not mergeable. Review the resolution on the opposite harness, run the fast checks against the current target tip, then use the merge queue. If `0.4` exists, repeat from `0.3` into `0.4`. Never force-push a release branch or infer a green result from its old tip. Until the queue is enabled, update to the target tip and rerun the same checks before an authorized merge.

Once `0.3` diverges, plan regular full rehearsals on its current head and again on the exact release-candidate tag before shipping. Record the exact commit and artifacts for install and reload from the version the daily machine runs, real-session behavior on an authorized test machine, and NVIDIA rendering on the designated hardware test machine. Obtain host access through the test-machine owner; never run the rehearsal on the daily machine. A failed or incomplete rehearsal blocks the release candidate, not unrelated fast-check work.
