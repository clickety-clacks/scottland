# Scottland on Omarchy

The `scottland-omarchy` package lets Scottland run on Omarchy beside Hyprland. Read the
`scottland` skill first: everything there holds. This skill covers only what the adapter adds or
changes. Hyprland, uwsm and Omarchy's own files are not modified by Scottland; Omarchy's shell,
menus, theme and wallpaper run unmodified inside it.

Which desktop is the user in? Inside Scottland `XDG_CURRENT_DESKTOP` starts with `Scottland`;
`scottland-exec --list` lists running Scottland sessions. With no session listed, the user is in
Hyprland, and the `omarchy` skill applies as usual.

## Which file to change

| The user wants... | Change |
|---|---|
| Something only in Scottland (a Scottland setting, a Scottland-only shortcut) | `~/.config/scottland/overrides.ini` (see the `scottland` skill) |
| A shortcut changed in both desktops | The Hyprland config, through the `omarchy` skill, with the user's OK. Scottland re-imports it within seconds. |
| Display scale, rotation or position in Scottland | `[output:NAME]` in `overrides.ini`. Hyprland's monitor settings don't apply in Scottland. |
| Theme, wallpaper, fonts | Omarchy as usual (`omarchy theme set ...`); Scottland follows the theme live. |

Never edit Hyprland or Omarchy files without the user's explicit OK. Never edit the adapter's
installed files (`/usr/lib/scottland`, `/usr/share/scottland-omarchy`).

## Shortcuts

At every Scottland session start, and whenever the Hyprland config changes, the adapter reads the
user's live Hyprland config (`~/.config/hypr/hyprland.lua`) and turns its shortcuts into Scottland
shortcuts. Nothing is copied at install.

- **Kept**: shortcuts that run commands (menus, launchers, media keys, screenshots, toggles),
  release shortcuts (push-to-talk, Super-release), shortcuts that run Lua functions (through the
  Scottland Lua host, `luahost.log`), and shortcuts a config turns on and off per app.
- **Not imported**: window navigation, tiling and layout, workspaces and window groups: Scottland
  has its own window management and no workspaces. Super+W (close) is left unbound so a single
  press can't close a window.
- **Collisions**: on keys Scottland's own features need (its `[scottland]` keys such as Super+M,
  Super+arrows, Alt+Tab; Super+, for Scottland Settings; Super+Ctrl+Alt+R reload; any per-app
  remap's key), Scottland's binding wins and the imported one steps aside. On any other key the
  user's Omarchy shortcut wins over Scottland's generic defaults.

The generated shortcuts are in `$XDG_RUNTIME_DIR/scottland/wayfire.ini`, after the line
`# ---- generated by 50-omarchy-shortcuts`.

### The override report

Every shortcut or mapping Scottland changes or can't import is listed, grouped by reason, in
`~/.local/state/scottland/omarchy-overrides.txt`. It starts with **Your own shortcuts that don't
work in Scottland** (entries marked `[Your custom/changed shortcut]`, including ones from
user-installed Omarchy plugins); the rest are Omarchy defaults (`[Omarchy default]`). Each entry says
what the key did in Omarchy, what it does in Scottland, and why. When the report's content changes,
the adapter opens it in the user's default coding agent with a prompt to walk them through it.

### Moving a displaced shortcut to a free key

Lead with the user's own shortcuts; explain each reason plainly; ask before changing anything.
For a shortcut Scottland displaced, either:

- give its action a free key in Scottland only, in `overrides.ini`:

  ```ini
  [command]
  binding_my_notes = <super> <shift> KEY_N
  command_my_notes = <the command the report entry names>
  ```

  (a key no imported or Scottland shortcut uses); or
- move Scottland's feature to another key (for example `minimize_widget = <super> KEY_N` under
  `[scottland]`), so the user's shortcut comes back on its original key.

Check the key is free first: search `$XDG_RUNTIME_DIR/scottland/wayfire.ini` (imported and
Scottland shortcuts) and `overrides.ini`. The report is regenerated after the change, and because
its content changed it opens again in the coding agent; tell the user what moved where.

## hyprctl and the Omarchy shell inside Scottland

A Hyprland shim serves Hyprland's IPC sockets from Scottland, so Omarchy's shell, its scripts and
`hyprctl` work in Scottland: `monitors`, `clients`, `activewindow`, `workspaces` (one),
`devices`, `getoption`, events, `dispatch exec`, and sending keys. Requests that move, tile or
focus windows the Hyprland way, or switch workspaces, have no Scottland meaning and aren't carried
out; the shim logs each request it can't handle as an `unsupported:` line in
`~/.local/state/scottland/hyprshim.log`. Use `scottland-ctl` (the `scottland` skill) to act on
Scottland's windows, not `hyprctl dispatch`.

Use `hyprctl` from a shell inside Scottland, or through `scottland-exec -- hyprctl ...` from
elsewhere; a shell from Hyprland talks to Hyprland.

Apps launched through Omarchy's launcher (`uwsm-app`) open in Scottland, and get the environment
the Hyprland config sets with `hl.env` (toolkit themes, Wayland hints, the user's own variables).

## Menus and keys

- Omarchy menu > System has **Switch Desktop**, **Reload Scottland** (only inside Scottland) and
  **Scottland Settings**. `scottland-omarchy-setup` adds them (once per user) and installs the
  Watercolor Dream Light and Dark themes if those names are free.
- Super+Escape in Scottland opens Omarchy's System menu.

## Switching between Scottland and Hyprland

`scottland-switch` opens the Switch Desktop dialog; `scottland-switch --to scottland` or
`--to hyprland` switches directly. **Switching always closes the current desktop and every window
in it**; there is no mode that keeps both desktops running. Always ask the user before switching,
and never switch on their behalf to test something. No password is needed. The machine boots into
whichever desktop was used last; if Scottland dies within seconds of starting, the next boot goes
to Hyprland. Handover log: `~/.local/state/scottland/handover.log`.

## Theme and notifications

- Scottland's palette (the widget cards, hint colors, attention color) follows the Omarchy theme
  live, including `omarchy theme set`. A theme's `colors.toml` may set `attention = "#rrggbb"`;
  otherwise its yellow is the attention color.
- Scottland's Sunlight setting, when enabled, switches between an Omarchy day theme and night
  theme (Watercolor Dream Light and Dark by default). Override either in
  `~/.config/scottland/omarchy-solar.ini`:

  ```ini
  [themes]
  day = watercolor-dream-light
  night = watercolor-dream-dark
  ```

  Don't run it alongside another theme scheduler.
- While a fullscreen window is in front, Scottland turns the Omarchy shell's do-not-disturb on, and
  back off afterwards; a do-not-disturb the user already had on stays on.

## What works and what doesn't

Works in Scottland: the Omarchy bar, menus, launcher, theme and wallpaper; command, release and
Lua-function shortcuts; `hyprctl` queries and `dispatch exec`; theme switching; app environment
from `hl.env`.

Not in Scottland:

- Workspaces, tiling, window groups and their shortcuts (by design).
- Hyprland settings other than shortcuts and `hl.env`: window rules, animations, gaps, decorations,
  input and monitor settings. Scottland's equivalents are in `~/.config/scottland/`.
- Keyboard layout switching and night light through the shim: not built yet.
- Omarchy scripts that ask Hyprland whether the session is locked don't see Scottland's lock yet.
- Window tags (`hyprctl dispatch` tag commands): not supported.

When a user reports an Omarchy feature not working in Scottland, check `hyprshim.log` and
`luahost.log` for `unsupported` lines or errors around that time, and the override report for the
key involved.
